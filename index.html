Pivot Selection & Optimization

01PROBLEM STATEMENT

Khi QuickSort chọn pivot không tốt

QuickSort dựa trên chia để trị: chọn một pivot, phân hoạch mảng rồi sắp xếp đệ quy hai phần. Trong cài đặt đơn giản nhất, pivot thường lấy tại đầu hoặc cuối mảng. Việc chọn rất rẻ, nhưng hoàn toàn không xét xem giá trị đó nằm ở đâu trong thứ tự của dữ liệu.

Với mảng tăng dần [1, 2, 3, 4, 5, 6, 7], chọn phần tử đầu 1 tạo hai phía có kích thước 0 và 6. Nếu tiếp tục theo cùng quy tắc, mỗi lần đệ quy chỉ loại đi một phần tử: n−1, n−2, …, 1. Tổng chi phí phân hoạch vì thế tăng bậc hai.

TRƯỜNG HỢP XẤUT(n) = T(n − 1) + Θ(n) = Θ(n²)
Có thể cải thiện chất lượng pivot mà vẫn giữ chi phí lựa chọn đủ thấp?
02WHY IT MATTERS

Không phải pivot lớn hay nhỏ — mà là hai phía có cân bằng không

Sau khi phân hoạch, pivot nằm đúng vị trí cuối cùng. Chi phí của một lần phân hoạch bằng Θ(n); sự khác biệt nằm ở kích thước hai bài toán con mà nó tạo ra.

Nếu mỗi lần pivot chia gần đôi, độ sâu đệ quy khoảng log₂n và tổng công việc là Θ(n log n). Nếu mỗi lần chỉ tách được một phần tử, độ sâu có thể lên tới n−1, dẫn đến Θ(n²).

Sơ đồ trực quan hóa độ sâu, không biểu diễn số phép so sánh chính xác của từng tầng.

03PROPOSED SOLUTION

Median-of-Three: chọn trung vị của ba mẫu

Thay vì chọn ngay phần tử đầu, lấy ba ứng viên ở vị trí lo, mid = lo + (hi−lo)/2 và hi. Giá trị đứng giữa trong ba ứng viên được chọn làm pivot. Đây là median (trung vị), không phải mean (trung bình cộng).

Với dãy tăng dần, ba ứng viên 1, 4, 7 cho trung vị 4, tạo hai phần có kích thước 3 : 3. Chi phí chọn pivot là một số hằng phép so sánh, thay vì phải tìm trung vị thật của toàn bộ mảng.

Trong mã Princeton, chỉ cần đưa giá trị trung vị về a[lo] trước khi gọi partition(): không cần viết lại thủ tục phân hoạch.

!Median-of-Three không tìm trung vị thật của mảng và không bảo đảm hai nửa cân bằng. Nó là một ước lượng rẻ, thường có ích trong thực tế.
04JAVA IMPLEMENTATION

Giữ nguyên phân hoạch, chỉ thay cách chọn pivot

Hai phiên bản dưới đây dùng cùng thủ tục 2-way partition kiểu Sedgewick với hai con trỏ i, j. Bản gốc đặt pivot tại a[lo]; bản cải tiến tìm trung vị rồi đổi về lo. Điều này giúp so sánh công bằng hơn so với việc thay cả thuật toán phân hoạch.

CODE 01

Phân hoạch gốc (Princeton, slide 13)

Xem file đầy đủ ↗
JAVA / two-way partition
private static int partition(int[] a, int lo, int hi) {
    int i = lo, j = hi + 1;

    while (true) {
        while (a[++i] < a[lo])
            if (i == hi) break;

        while (a[lo] < a[--j])
            if (j == lo) break;

        if (i >= j) break;
        exch(a, i, j);
    }

    exch(a, lo, j);
    return j;
}

Chuyển kiểu dữ liệu từ Comparable[] trong slide sang int[] để thuận tiện cho trình diễn; cấu trúc phân hoạch được giữ nguyên. Không nên gọi đây là phân hoạch Lomuto.

CODE 02

Điểm thay đổi để dùng Median-of-Three

JAVA / median-of-three
private static void sort(int[] a, int lo, int hi,
                         Strategy strategy) {
    if (hi <= lo) return;

    if (strategy == Strategy.MEDIAN_OF_THREE) {
        int mid = lo + (hi - lo) / 2;
        int median = medianOf3(a, lo, mid, hi);
        exch(a, lo, median);
    }

    int j = partition(a, lo, hi);
    sort(a, lo, j - 1, strategy);
    sort(a, j + 1, hi, strategy);
}

private static int medianOf3(int[] a, int i, int j, int k) {
    if (a[i] < a[j]) {
        if (a[j] < a[k]) return j;
        return a[i] < a[k] ? k : i;
    }
    if (a[i] < a[k]) return i;
    return a[j] < a[k] ? k : j;
}

Slide 28 nêu rõ thao tác medianOf3 → swap(a, lo, median) → partition; hàm medianOf3 đầy đủ được bổ sung trong repo. Nếu muốn giữ bảo đảm kỳ vọng trước đầu vào đối kháng, có thể shuffle trước như bản gốc ở slide 15.

05INTERACTIVE EXPERIMENT

Chạy cùng một mảng, so sánh hai chiến lược

06MATHEMATICAL ANALYSIS

Lợi ích kỳ vọng sau khi tính cả chi phí chọn pivot

Trên mô hình các khóa phân biệt với thứ tự đầu vào ngẫu nhiên đều, thứ hạng tương đối của pivot lấy ngẫu nhiên một mẫu tiệm cận phân bố đều. Nếu lấy ba mẫu ngẫu nhiên rồi chọn trung vị, phân bố thứ hạng pivot tập trung quanh một nửa hơn.

Pivot có thể nằm gần một trong hai biên với xác suất tương đối cao.

Mật độ lớn nhất tại x = 1/2, nơi phân hoạch cân bằng nhất.

07LIMITATIONS & ENGINEERING

Median-of-Three tốt hơn, nhưng không miễn nhiễm trường hợp xấu

01 / WORST-CASE

Vẫn có thể lệch mạnh

Nếu ba mẫu có giá trị nhỏ nhất, nhỏ thứ hai và lớn nhất, trung vị của ba mẫu vẫn chỉ là phần tử nhỏ thứ hai. Có thể thiết kế dữ liệu khiến những tình huống bất lợi tiếp tục tái diễn: worst-case vẫn là Θ(n²).

02 / EQUAL KEYS

Nhiều khóa trùng

Chọn pivot tốt không tự giải quyết vấn đề các khóa bằng nhau. Slide 42–47 đề xuất Dijkstra 3-way partitioning, chia thành ba nhóm <v, =v, >v để xử lý trường hợp này hiệu quả hơn.

03 / SMALL SUBARRAYS

Overhead của mảng nhỏ

Đối với mảng con rất nhỏ, chọn pivot và đệ quy có thể đắt hơn lợi ích mang lại. Slide 27 khuyến nghị chuyển sang Insertion Sort gần ngưỡng 10 phần tử; ngưỡng tối ưu phụ thuộc môi trường.

FURTHER ENGINEERING

Từ Median-of-Three đến system sort

Slide 53 giới thiệu hướng Bentley–McIlroy: ngưỡng Insertion Sort, Median-of-Three hoặc Tukey’s ninther, kết hợp phân hoạch ba chiều. Slide 63 còn chỉ ra rằng số phép so sánh không quyết định tất cả: số lần trao đổi và đặc biệt khả năng tận dụng cache cũng ảnh hưởng đến thời gian thực tế.

08CONCLUSION & REFERENCES

Kết luận

Lựa chọn pivot là một trong những quyết định quan trọng nhất khi triển khai QuickSort. Pivot cố định ở đầu mảng đơn giản nhưng dễ gây phân hoạch lệch trên dữ liệu đã có thứ tự nếu không được shuffle. Median-of-Three là một cải tiến có chi phí thấp: lấy trung vị của ba ứng viên rồi dùng lại chính thủ tục phân hoạch gốc.

Trong mô hình ngẫu nhiên phù hợp, hệ số dẫn đầu của số phép so sánh giảm từ 2 xuống 12/7, tức khoảng 14,29%, kể cả khi tính chi phí chọn mẫu vào bậc thấp. Tuy nhiên, kỹ thuật không thay đổi worst-case Θ(n²) và không bảo đảm giảm thời gian chạy trong mọi trường hợp.

TAKEAWAYMột pivot “thông minh” không nhất thiết phải hoàn hảo; nó cần đủ tốt để bù lại chi phí chọn nó.
